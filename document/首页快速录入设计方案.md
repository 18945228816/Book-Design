# 首页快速录入设计方案

最后更新：2026-05-02

## 1. 目标

在当前项目中，首页已经承担了“系统入口”的角色，但还没有真正承担“记录入口”的角色。  
本方案的目标是把“快速录入”从一个概念功能，落成首页上的高频操作能力，让用户在产生灵感时可以先快速记下来，再在后续场景中慢慢完善。

核心目标如下：

- 用户进入首页后，无需跳转页面即可完成一次快速记录
- 首次录入控制在 5 到 15 秒内完成
- 支持“先保存草稿，后续再整理”
- 每一条记录都必须关联到书中的具体位置，不能成为脱离原文上下文的孤立素材
- 在书籍详情页中，能回到素材对应的位置，并对命中的原文片段做高亮展示
- 尽量复用当前素材体系，而不是新造一套独立数据结构
- 后续可平滑扩展到语音录入、图片录入、AI 引导完善

## 2. 当前项目现状

结合当前代码，现状如下：

- 首页 [frontend/src/views/Home.vue](/abs/path/c:/Users/admin/Desktop/Book-Design/frontend/src/views/Home.vue) 只有欢迎区、统计卡片、最近素材，没有录入能力
- 素材新增目前主要在 [frontend/src/views/Materials.vue](/abs/path/c:/Users/admin/Desktop/Book-Design/frontend/src/views/Materials.vue) 中通过弹窗完成
- 书籍详情页 [frontend/src/views/BookDetail.vue](/abs/path/c:/Users/admin/Desktop/Book-Design/frontend/src/views/BookDetail.vue) 已支持“在阅读上下文中记录素材”
- 后端 `materials` 目前只有 `content / source_type / book_id / chapter_order / note / tags / created_at`
- 现有文档已经多次提到“快速录入”“草稿态”，但真实后端还没有 `status=draft` 这层支持

这说明项目已经有“素材记录”的主链路，但缺少两个关键能力：

- 首页录入入口
- 草稿态管理能力
- 细粒度的位置锚点和位置高亮能力

## 3. 设计原则

首页快速录入不应该做成“简化版素材页”，而应该做成“捕捉灵感”的第一落点。

建议遵循以下原则：

- 先记录，后整理：优先降低输入门槛，不要求首次输入就很完整
- 首页常驻：入口必须在首屏可见，而不是藏在二级按钮里
- 最少字段：默认只录最必要信息，更多字段在展开态或后续编辑中完成
- 无定位不入库：所有内容都必须绑定到某本书、某一章、某一段或某一段文本范围
- 感悟也要挂点：即便是“自己感悟”，也必须指向触发这条感悟的原文位置
- 与素材库打通：快速录入的数据最终仍然进入 `materials`

## 4. 推荐方案

### 4.1 页面位置

建议把首页 Hero 区改为左右布局：

- 左侧保留欢迎文案、书籍入口、素材入口
- 右侧新增“快速录入卡片”

这样可以保证“首页一打开就能录”，同时不破坏当前首页作为导航页的定位。

### 4.2 首页新增模块

建议在首页新增两个模块：

#### 模块 A：快速录入卡片

这是首页首屏的核心交互，默认常驻展示。

建议字段如下：

- `content`：多行输入框，支持直接粘贴一句话、一段摘录、一个模糊感受
- `source_type`：来源类型切换
  - `自己感悟`
  - `书摘`
  - `微信读书`
- `book_id`：必填，选择当前关联书籍
- `chapter_order`：必填，选择具体章节
- `selected_text`：选填但强烈建议，由用户粘贴对应原句，或从章节阅读页带入
- `anchor_range`：系统字段，保存高亮定位范围
- `note`：默认折叠，点击“补充想法”后展开

建议按钮如下：

- `保存草稿`
- `保存并完善`
- `去素材库查看`

建议默认交互如下：

- 用户进入首页即可看到输入框
- 输入框获得焦点后，展示来源选择、书籍选择和定位字段
- 书籍选定后，才允许保存
- 章节选定后，才允许保存
- 如果没有 `selected_text`，允许先保存草稿，但必须至少保留章节定位
- 点击“保存草稿”后，立即清空输入框并给出成功反馈
- 点击“保存并完善”后，保存成功并跳转到素材编辑场景

#### 模块 B：最近草稿

建议放在“最近素材”模块上方或并列位置，展示最近 3 到 5 条草稿。

每条草稿展示：

- 草稿内容前 1 到 2 行
- 来源类型
- 关联书籍
- 关联章节/位置摘要
- 最后更新时间
- 操作按钮：`继续完善`、`直接完成`

这样首页不只是录入入口，也是“重新捡起未完成想法”的入口。

## 5. 交互流程设计

### 5.1 场景一：突然有一个想法

流程如下：

1. 用户进入首页
2. 在快速录入框中输入一句话
3. 保持默认来源 `自己感悟`
4. 点击 `保存草稿`
5. 系统提示“已保存到草稿”
6. 该条内容进入“最近草稿”

这个流程应该控制在 5 秒左右。

### 5.2 场景二：记录一本书里的摘录

流程如下：

1. 用户在首页粘贴一句摘录
2. 将来源切换为 `书摘`
3. 选择关联书籍
4. 选择关联章节，最好再粘贴对应原句
5. 点击 `保存草稿`
6. 后续在素材页继续补充自己的理解或备注

这个流程重点是“先建立关联，再慢慢完善”。

### 5.3 场景三：用户想一次录完

流程如下：

1. 用户输入内容
2. 选择来源
3. 选择书籍和章节位置
4. 补充备注
5. 点击 `保存并完善`
6. 系统创建素材并跳转到编辑弹窗或编辑页
7. 用户补全标签、修改内容、确认完成

这个流程适合当前已经想清楚、希望一次成稿的用户。

### 5.4 场景四：从素材回到书中定位

流程如下：

1. 用户在首页、素材页或书籍详情页点击某条素材的“查看原文位置”
2. 系统跳转到对应书籍详情页，并自动打开对应章节
3. 系统将素材绑定的原文范围高亮展示
4. 若素材只有章节级定位，没有精确文本范围，则滚动到该章节顶部并提示“未定位到精确片段”

这个流程是“所有内容必须可追溯到原文位置”的关键闭环。

## 6. 数据设计

### 6.1 推荐最小改造

当前 `materials` 模型已经足够承接快速录入，不建议单独新建 `quick_entries` 表。  
推荐直接扩展 `materials`，增加以下字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `status` | String(20) | 素材状态：`draft` / `completed` |
| `updated_at` | DateTime | 最近修改时间，用于草稿排序 |
| `entry_mode` | String(20) | 来源场景：`home_quick` / `book_detail` / `materials_page` |
| `selected_text` | Text | 用户绑定的原文片段 |
| `anchor_start` | Integer | 在章节内容中的起始字符位置 |
| `anchor_end` | Integer | 在章节内容中的结束字符位置 |
| `locator_text` | String(255) | 位置摘要，例如“第 12 章 第 3 段” |

### 6.2 字段含义建议

- `content`
  - 对于草稿：保存用户原始输入
  - 对于完成态：保存用户最终确认的素材内容
- `note`
  - 保存补充想法、上下文或后续备注
- `book_id + chapter_order`
  - 最低级别的位置约束
  - 每条素材都必须存在
- `selected_text`
  - 用于展示用户到底是对哪一句、哪一段产生了记录
- `anchor_start / anchor_end`
  - 用于前端在章节文本中精确高亮
- `status`
  - `draft`：用户只是先记下来，尚未整理完成
  - `completed`：用户已确认该条内容可以进入正式素材库视图

### 6.3 为什么不单独建表

原因如下：

- 当前项目已有完整的素材 CRUD
- 快速录入和正式素材本质上是同一类内容，只是成熟度不同
- 单表可以减少前后端维护成本
- 后续筛选时只需按 `status` 区分即可

## 7. 接口设计

## 7.1 推荐做法

优先扩展现有素材接口，而不是新增一套独立接口。

### 7.2 新增或调整的请求字段

当前 `POST /api/v1/materials` 建议扩展支持：

```json
{
  "content": "先记下一句话",
  "source_type": "自己感悟",
  "book_id": "uuid",
  "chapter_order": 12,
  "selected_text": "触发这条记录的原文句子",
  "anchor_start": 120,
  "anchor_end": 168,
  "note": "可选备注",
  "status": "draft",
  "entry_mode": "home_quick"
}
```

约束建议如下：

- `book_id` 必填
- `chapter_order` 必填
- `selected_text` 非必填，但如果传入则后端应尝试校验它是否出现在对应章节中
- `anchor_start / anchor_end` 非必填，但如果传入则应校验范围合法

### 7.3 列表接口扩展

当前 `GET /api/v1/materials` 建议新增查询参数：

- `status`
- `limit`

示例：

```http
GET /api/v1/materials?status=draft&limit=5
```

用于首页加载最近草稿。

### 7.4 更新接口

当前 `PATCH /api/v1/materials/{id}` 建议支持：

- 修改 `content`
- 修改 `note`
- 修改 `tags`
- 修改 `status`
- 修改 `selected_text`
- 修改 `anchor_start / anchor_end`
- 修改 `chapter_order`

这样一条草稿就可以在完善后从 `draft` 变成 `completed`。

### 7.5 新增定位接口建议

为了让前端更稳定地高亮，建议增加一个定位查询接口：

```http
GET /api/v1/materials/{id}/location
```

返回示例：

```json
{
  "book_id": "uuid",
  "book_title": "书名",
  "chapter_order": 12,
  "chapter_title": "章节标题",
  "selected_text": "触发记录的原文句子",
  "anchor_start": 120,
  "anchor_end": 168,
  "locator_text": "第12章 第3段"
}
```

## 8. 前端设计

### 8.1 组件拆分建议

为了避免首页逻辑继续膨胀，建议提炼一个可复用组件：

- `frontend/src/components/QuickEntryPanel.vue`

职责如下：

- 输入内容
- 选择来源类型
- 选择关联书籍
- 选择关联章节
- 维护原文定位信息
- 保存草稿
- 保存并完善

首页 `Home.vue` 只负责：

- 拉取统计数据
- 拉取最近素材
- 拉取最近草稿
- 承载 `QuickEntryPanel`

### 8.2 首页交互建议

建议首页视觉结构调整为：

- Hero 左侧：品牌文案 + 入口按钮
- Hero 右侧：快速录入卡片
- 下方：统计卡片
- 再下方：最近草稿 + 最近素材

这样信息层级会更合理：

- 第一层：我现在就能记
- 第二层：我系统里已经积累了多少
- 第三层：我最近记了什么、还有什么没整理

### 8.3 保存后的反馈

建议区分两类反馈：

- 保存草稿成功：提示 `已保存到草稿，可稍后继续完善`
- 保存完成成功：提示 `素材已保存`
- 定位不完整时：提示 `已保存章节位置，建议补充原文片段以支持精确高亮`

并增加以下细节：

- 成功后重置输入框
- 刷新首页“最近草稿”或“最近素材”
- 保存时禁用按钮，防止重复提交

### 8.4 书中高亮展示

这是这次新增要求里的核心能力。

建议在 [frontend/src/views/BookDetail.vue](/abs/path/c:/Users/admin/Desktop/Book-Design/frontend/src/views/BookDetail.vue) 中增加以下能力：

- 支持从路由参数接收 `materialId`
- 页面加载后，根据 `materialId` 拉取素材定位信息
- 自动打开对应章节
- 在章节正文中根据 `anchor_start / anchor_end` 对命中文本做高亮
- 若只有 `selected_text` 没有范围，则在章节内做首次匹配并高亮
- 若两者都没有，只能退化为章节级定位

推荐路由形式：

```text
/books/:id?chapter=12&material=xxx
```

高亮渲染建议：

- 非高亮文本按普通段落输出
- 命中片段使用 `mark` 或自定义 `span.highlight`
- 页面进入后自动滚动到高亮片段附近
- 高亮颜色与当前阅读区分明显，但不要破坏正文可读性

## 10. 与当前项目的差异说明

这部分很重要，因为当前“文档设想”和“真实代码”并不完全一致。

当前文档里已经出现过以下设定：

- 素材有 `draft/completed`
- 快速录入会先存草稿

但当前真实实现里：

- `materials` 没有 `status`
- `materials` 也没有精确定位字段
- 素材列表接口也不支持按 `status` 查询
- 首页没有录入入口
- 书籍详情页只能定位到章节，不能高亮到具体片段

所以这次首页快速录入，建议按“补基础能力 + 做首页入口”的顺序推进，而不是只做一个前端输入框。

## 11. 分阶段实施建议

### Phase 1：MVP

目标：先让首页能快速记，并能保存为草稿。

范围如下：

- 首页新增快速录入卡片
- 后端 `materials` 增加 `status / updated_at / entry_mode`
- 后端 `materials` 增加位置锚点字段
- 素材创建接口支持 `status`
- 素材创建接口要求 `book_id + chapter_order`
- 素材列表接口支持 `status`
- 首页展示最近草稿

这一阶段完成后，功能就已经可用。

### Phase 2：完善体验

范围如下：

- `保存并完善` 跳转到指定素材编辑态
- 素材页增加“草稿”筛选
- 草稿支持批量完成或删除
- 书籍详情页支持素材定位高亮
- 增加快捷键触发快速录入

### Phase 3：智能增强

范围如下：

- 语音转文字
- 图片 OCR 摘录
- AI 自动润色草稿
- AI 引导用户把草稿扩展成可复用表达

## 12. 验收标准

首页快速录入功能完成后，至少应满足以下标准：

- 首页首屏可见快速录入区域
- 用户可以不跳转页面完成一次录入
- 可以明确区分“草稿”和“正式素材”
- 草稿可以在后续被继续完善
- 所有录入都必须关联书籍和章节位置
- 有精确锚点的素材可以在书籍详情页高亮原文片段
- 没有精确锚点的素材也至少能回到对应章节
- 首页可以看到最近草稿

## 13. 推荐结论

推荐采用下面这条路线：

- 首页直接放常驻“快速录入卡片”
- 后端以扩展 `materials` 为主，不新建独立表
- 先实现 `draft/completed` 两态
- 同时把“章节定位 + 片段高亮”作为基础能力一并做掉
- 先做文字版 MVP，再扩展语音和图片

这是当前项目里投入最小、收益最高、也最容易继续往下迭代的一种设计。
